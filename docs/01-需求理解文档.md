## 1. 项目背景

### 1.1 业务场景
在现代分布式系统架构中，各个业务系统之间需要进行事件通知和数据同步。传统的同步调用方式存在以下问题：
- 系统间耦合度高，难以维护
- 性能瓶颈，影响主流程响应
- 容错性差，一个系统故障影响整体

### 1.2 解决方案
构建一个**独立的API通知系统**，作为事件分发中心：
- 业务系统只需将事件发布到通知系统
- 通知系统负责异步推送给订阅方
- 实现业务系统与外部系统的解耦

## 3. 需求描述分析

### 3.1 功能性需求

根据PDF中的**<需求描述>**章节，系统需要实现以下核心功能：

#### 3.1.1 订阅管理
**功能描述**：外部系统可以注册订阅，指定关注的事件类型和回调地址。

**详细需求**：
- 订阅者可以注册回调URL
- 可以选择订阅一个或多个事件类型
- 支持订阅信息的增删改查
- 支持订阅的启用/禁用状态管理
- 每个订阅应有唯一标识

**输入**：
- 订阅者名称/标识
- 回调URL（必须是有效的HTTP/HTTPS地址）
- 订阅的事件类型列表
- 可选的认证信息（如签名密钥）

**输出**：
- 订阅ID
- 订阅状态
- 创建时间

#### 3.1.2 事件发布
**功能描述**：业务系统在特定事件发生时，将事件发布到通知系统。

**详细需求**：
- 业务系统通过API发布事件
- 支持同步发布（接口立即返回）
- 事件应包含类型、时间戳、业务数据
- 事件持久化存储
- 发布接口应高性能、低延迟

**输入**：
- 事件类型（如：USER_REGISTERED, ORDER_CREATED）
- 事件数据（JSON格式）
- 事件时间戳
- 业务ID（用于追踪）

**输出**：
- 事件ID
- 发布状态
- 发布时间

#### 3.1.3 通知推送
**功能描述**：系统异步向订阅者推送事件通知。

**详细需求**：
- 事件发布后，系统自动匹配订阅者
- 异步向订阅者的回调URL发送HTTP POST请求
- 通知内容包含完整的事件信息
- 支持并发推送（多个订阅者同时推送）
- 推送超时时间可配置（如30秒）

**通知格式**：
```json
{
  "eventId": "evt_123456",
  "eventType": "ORDER_CREATED",
  "timestamp": "2026-09-06T10:30:00Z",
  "data": {
    "orderId": "ORD001",
    "amount": 299.00,
    "userId": "USR123"
  },
  "signature": "abc123..." // 可选的签名
}
```

#### 3.1.4 重试机制
**功能描述**：通知发送失败时，自动进行重试。

**详细需求**：
- 失败判定条件：
  - HTTP状态码非2xx
  - 网络超时
  - 连接失败
- 重试策略：
  - 指数退避算法（1分钟、5分钟、15分钟、1小时）
  - 最大重试次数可配置（如5次）
  - 超过最大次数后标记为失败
- 重试期间不阻塞新事件处理

#### 3.1.5 通知记录与查询
**功能描述**：记录所有通知的发送历史，支持查询和追踪。

**详细需求**：
- 记录每次通知的详细信息：
  - 事件ID、订阅者ID
  - 推送时间、响应时间
  - HTTP状态码、响应内容
  - 重试次数
  - 最终状态（成功/失败）
- 支持按多维度查询：
  - 按事件ID查询
  - 按订阅者查询
  - 按时间范围查询
  - 按状态查询
- 支持分页查询

#### 3.1.6 监控与告警
**功能描述**：提供系统运行状态监控和异常告警。

**详细需求**：
- 统计信息：
  - 事件发布量（按类型、按时间）
  - 通知成功率
  - 平均推送延迟
  - 重试次数统计
- 告警规则：
  - 某订阅者连续失败N次告警
  - 系统队列积压告警
  - 推送延迟超过阈值告警

### 3.2 非功能性需求

#### 3.2.1 性能要求
- **高吞吐量**：支持每秒1000+事件发布
- **低延迟**：事件发布接口响应时间 < 100ms
- **推送延迟**：正常情况下事件发布后1秒内开始推送

#### 3.2.2 可靠性要求
- **消息不丢失**：事件持久化存储
- **至少一次送达**：保证通知至少发送一次（可能重复）
- **系统可用性**：99.9%以上

#### 3.2.3 可扩展性要求
- **水平扩展**：支持通过增加实例提升处理能力
- **动态配置**：事件类型、重试策略支持动态配置
- **多租户**：支持多个业务系统接入

#### 3.2.4 安全性要求
- **认证授权**：API访问需要认证
- **签名验证**：推送通知支持签名，防止伪造
- **HTTPS**：生产环境强制使用HTTPS
- **敏感数据**：敏感信息加密存储

#### 3.2.5 可维护性要求
- **日志完整**：关键操作记录详细日志
- **链路追踪**：事件全链路可追踪
- **配置外置**：配置与代码分离
- **代码规范**：遵循编码规范，注释完整

## 4. 系统边界

### 4.1 系统职责
本系统负责：
- ✅ 接收事件发布请求
- ✅ 管理订阅关系
- ✅ 异步推送通知
- ✅ 失败重试
- ✅ 记录通知历史
- ✅ 提供查询接口

### 4.2 系统不负责
本系统不负责：
- ❌ 具体业务逻辑处理
- ❌ 订阅者的回调接口实现
- ❌ 事件内容的校验（由业务系统负责）
- ❌ 订阅者的认证授权（订阅者自行实现）

### 4.3 对外依赖
- **业务系统**：作为事件发布方
- **外部系统**：作为订阅方（提供HTTP回调接口）
- **数据库**：持久化存储
- **消息队列**（可选）：用于异步任务处理

## 5. 核心概念定义

### 5.1 事件（Event）
系统中发生的一个有意义的状态变化，包含：
- **事件类型**（Event Type）：如USER_REGISTERED、ORDER_CREATED
- **事件数据**（Event Data）：具体的业务数据
- **时间戳**：事件发生的时间

### 5.2 订阅（Subscription）
外部系统对特定事件的订阅关系，包含：
- **订阅者标识**：唯一标识订阅者
- **回调URL**：接收通知的地址
- **订阅的事件类型列表**
- **状态**：启用/禁用

### 5.3 通知（Notification）
向订阅者发送的一次HTTP回调请求，包含：
- **事件信息**：完整的事件数据
- **推送状态**：待推送、推送中、成功、失败
- **重试信息**：重试次数、下次重试时间

## 6. 典型使用场景

### 场景1：用户注册通知
1. 用户在业务系统完成注册
2. 业务系统发布USER_REGISTERED事件到通知系统
3. 通知系统查找订阅了USER_REGISTERED的订阅者
4. 异步向各订阅者推送通知
5. CRM系统收到通知，创建客户档案
6. 邮件系统收到通知，发送欢迎邮件

### 场景2：订单支付通知
1. 用户完成支付
2. 支付系统发布ORDER_PAID事件
3. 通知系统推送给订单系统、库存系统、物流系统
4. 如果物流系统回调失败，自动重试
5. 重试5次后仍失败，记录失败状态并告警

### 场景3：查询通知历史
1. 业务人员需要排查某个订单的通知情况
2. 通过事件ID或订单ID查询通知记录
3. 查看每个订阅者的推送状态和响应详情
4. 定位问题原因（如订阅者服务不可用）

## 7. 关键设计要点

### 7.1 事件驱动
- 采用事件驱动架构
- 事件发布与处理异步解耦
- 通过消息队列实现异步处理

### 7.2 业务解耦
- 通知系统不包含任何业务逻辑
- 只负责事件的可靠传递
- 业务系统通过标准API接入

### 7.3 高可用设计
- 事件持久化，防止丢失
- 支持多实例部署
- 失败重试机制
- 完整的监控告警

### 7.4 可扩展设计
- 支持动态添加事件类型
- 订阅关系可动态配置
- 支持多种推送策略
