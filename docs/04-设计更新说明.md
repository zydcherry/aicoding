## 重要更新：系统定位调整

### 📋 问题发现

在设计适配器模块时，我们最初加入了钉钉、企微等IM平台的适配器。经过深入分析PDF需求后发现，这是对需求的**误解**。

### ✅ 正确理解

**PDF需求中的"不同供应商API格式"指的是**：
- 不同的**业务系统**（CRM、ERP、物流、财务等）
- 它们的**HTTP API格式**各不相同
- 需要适配器做格式转换

**而不是**：
- ❌ 钉钉、企微等IM平台
- ❌ 消息推送服务
- ❌ 人员通知工具

---

## 系统定位明确

### ✅ 本系统专注于：B2B业务系统集成

**核心场景**：
```
订单系统 → 通知系统 → CRM系统（API回调）
                  ↓
              物流系统（API回调）
                  ↓
              财务系统（API回调）
```

**特点**：
- 系统到系统的通信
- 结构化数据传递
- 需要可靠性保证
- 需要幂等性支持

**典型订阅者**：
- CRM系统：需要同步客户信息
- 物流系统：需要接收发货通知
- 财务系统：需要接收支付通知
- 第三方合作伙伴系统：需要接收业务事件

### ❌ 本系统不包含：人员消息推送

**不包括的场景**：
```
订单系统 → 通知系统 → 钉钉群（消息推送）❌
                  ↓
              企微群（消息推送）❌
                  ↓
              邮件通知（消息推送）❌
```

**原因**：
1. **职责不同**：系统集成 vs 消息推送是两个不同的业务域
2. **可靠性要求不同**：系统集成需要强一致性，消息推送允许丢失
3. **数据格式不同**：API传递结构化数据，消息推送传递可读文本
4. **架构复杂度**：混合会导致职责不清、难以维护

## 设计调整

### 移除的内容

**删除的适配器**：
- ❌ DingTalkAdapter（钉钉适配器）
- ❌ WeComAdapter（企微适配器）
- ❌ SlackAdapter（Slack适配器）

### 保留的内容

**核心适配器**：
- ✅ **StandardAdapter**（标准格式）- 适用于自建系统或遵循标准格式的第三方系统
- ✅ **CustomTemplateAdapter**（自定义模板）- 通过模板配置适配任意第三方API格式

**充分性说明**：
这两个适配器已经能够覆盖所有B2B系统集成场景：
- 标准格式：80%的情况适用
- 自定义模板：可以适配剩余20%的任意格式

## 适配器应用示例

### 场景1：标准格式 - CRM系统

**订阅配置**：
```json
{
  "subscriberName": "CRM系统",
  "callbackUrl": "https://crm.example.com/webhook",
  "eventTypes": ["USER_REGISTERED"],
  "vendorType": "STANDARD"
}
```

**推送格式**：
```json
{
  "eventId": "evt_123",
  "eventType": "USER_REGISTERED",
  "timestamp": "2026-09-06T10:30:00Z",
  "data": {
    "userId": "USR001",
    "username": "zhangsan",
    "email": "zhangsan@example.com"
  }
}
```

### 场景2：自定义格式 - 物流系统

**需求**：物流系统的API要求不同的字段名和结构

**订阅配置**：
```json
{
  "subscriberName": "物流系统",
  "callbackUrl": "https://logistics.example.com/api/order-events",
  "eventTypes": ["ORDER_CREATED"],
  "vendorType": "CUSTOM",
  "adapterConfig": {
    "bodyTemplate": "{\"eventId\":\"${eventId}\",\"eventType\":\"${eventType}\",\"payload\":${eventData},\"orderId\":\"${data.orderId}\"}",
    "headerMapping": {
      "X-API-Key": "logistics_api_key_123"
    },
    "authType": "API_KEY",
    "authConfig": {
      "apiKey": "logistics_api_key_123",
      "headerName": "X-API-Key"
    }
  }
}
```

**推送格式**：
```json
{
  "eventId": "evt_456",
  "eventType": "ORDER_CREATED",
  "payload": {
    "orderId": "ORD001",
    "userId": "USR123",
    "amount": 299.00
  },
  "orderId": "ORD001"
}
```

### 场景3：自定义格式 - 财务系统（扁平结构）

**需求**：财务系统要求扁平的JSON结构，字段名使用下划线

**订阅配置**：
```json
{
  "subscriberName": "财务系统",
  "callbackUrl": "https://finance.example.com/webhooks/payments",
  "eventTypes": ["ORDER_PAID"],
  "vendorType": "CUSTOM",
  "adapterConfig": {
    "bodyTemplate": "{\"event_id\":\"${eventId}\",\"event_type\":\"${eventType}\",\"order_id\":\"${data.orderId}\",\"amount\":\"${data.amount}\",\"user_id\":\"${data.userId}\"}",
    "headerMapping": {
      "Authorization": "Bearer finance_token_xyz"
    },
    "authType": "BEARER",
    "authConfig": {
      "token": "finance_token_xyz"
    }
  }
}
```

**推送格式**：
```json
{
  "event_id": "evt_789",
  "event_type": "ORDER_PAID",
  "order_id": "ORD001",
  "amount": "299.00",
  "user_id": "USR123"
}
```

## 设计原则反思

### 1. YAGNI原则（You Aren't Gonna Need It）
- **问题**：我们添加了可能永远用不到的IM平台适配器
- **教训**：不要过度设计，只实现当前明确需要的功能

### 2. 单一职责原则
- **问题**：一个系统同时负责系统集成和消息推送
- **教训**：一个系统只做一件事，并把它做好

### 3. 深入理解需求
- **问题**："不同供应商API格式" 被误解为 "不同消息平台"
- **教训**：要深入理解业务场景，不要想当然

### 4. 边界清晰
- **问题**：混淆了核心功能和扩展功能
- **教训**：明确什么是核心、什么是扩展、什么是不相关

## 扩展性考虑

### 如果将来确实需要IM平台集成

**推荐方式**：作为独立的扩展模块

```java
/**
 * IM平台扩展模块（可选）
 * 默认不启用，需要显式配置
 */
@Configuration
@ConditionalOnProperty(
    name = "notification.extension.im.enabled", 
    havingValue = "true"
)
public class IMExtensionModule {
    // 钉钉、企微等扩展适配器
    // 明确标注为扩展功能
}
```

**设计要点**：
1. 作为可选扩展，默认不加载
2. 与核心系统解耦，独立维护
3. 不影响核心系统的稳定性和简洁性

- 预留扩展接口
