## 1. 产品概述

### 1.1 产品定位
API通知系统是一个**独立的事件分发中间件**，为业务系统提供事件驱动的异步通知能力，实现业务系统与外部系统的解耦。

### 1.2 产品价值
- **降低耦合度**：业务系统无需关心订阅者的实现细节
- **提升可靠性**：统一的重试机制和错误处理
- **提高性能**：异步处理不阻塞主业务流程
- **简化集成**：标准化的API接口，易于接入

### 1.3 目标用户
- **业务系统开发者**：需要发布事件通知
- **外部系统开发者**：需要订阅业务事件
- **运维人员**：需要监控系统运行状态
- **业务人员**：需要查询通知记录

## 3. 核心功能设计

### 3.1 订阅管理

#### 3.1.1 创建订阅
**功能说明**：外部系统注册订阅，指定关注的事件类型和回调地址。

**操作流程**：
```
订阅者 → 提交订阅信息 → 系统验证 → 创建订阅记录 → 返回订阅ID
```

**输入信息**：
- 订阅者名称（必填）
- 回调URL（必填，需验证格式）
- 订阅事件类型（必填，可多选）
- 描述说明（可选）
- 密钥（可选，用于签名验证）

**验证规则**：
- URL格式必须合法（http://或https://）
- 事件类型必须在系统支持的类型列表中
- 同一订阅者对同一事件类型不能重复订阅

**输出结果**：
```json
{
  "subscriptionId": "sub_123456",
  "status": "ACTIVE",
  "createdAt": "2026-09-06T10:30:00Z",
  "message": "订阅创建成功"
}
```

#### 3.1.2 查询订阅
**功能说明**：查询已创建的订阅信息。

**查询方式**：
- 按订阅ID查询（精确查询）
- 按订阅者名称查询（模糊查询）
- 按事件类型查询（筛选）
- 按状态查询（启用/禁用）

**返回信息**：
```json
{
  "subscriptions": [
    {
      "subscriptionId": "sub_123456",
      "subscriberName": "CRM系统",
      "callbackUrl": "https://crm.example.com/webhook",
      "eventTypes": ["USER_REGISTERED", "USER_UPDATED"],
      "status": "ACTIVE",
      "createdAt": "2026-09-06T10:30:00Z",
      "updatedAt": "2026-09-06T10:30:00Z"
    }
  ],
  "total": 1,
  "page": 1,
  "pageSize": 10
}
```

#### 3.1.3 更新订阅
**功能说明**：修改订阅信息（回调URL、事件类型、状态等）。

**可修改字段**：
- 回调URL
- 订阅的事件类型
- 状态（启用/禁用）
- 密钥

**不可修改字段**：
- 订阅ID
- 订阅者名称
- 创建时间

#### 3.1.4 删除订阅
**功能说明**：删除不再需要的订阅。

**删除规则**：
- 软删除（标记为已删除，保留历史数据）
- 删除后不再接收该订阅的通知
- 历史通知记录仍可查询

### 3.2 事件发布

#### 3.2.1 发布事件
**功能说明**：业务系统发布事件到通知系统。

**操作流程**：
```
业务系统 → 发布事件 → 接收验证 → 持久化存储 → 触发异步推送 → 返回成功
```

**时序要求**：
- 接口同步返回（< 100ms）
- 不等待推送完成
- 异步进行订阅匹配和推送

**请求格式**：
```json
{
  "eventType": "ORDER_CREATED",
  "eventData": {
    "orderId": "ORD20260906001",
    "userId": "USR123",
    "amount": 299.00,
    "orderTime": "2026-09-06T10:30:00Z"
  },
  "businessId": "ORD20260906001",
  "timestamp": "2026-09-06T10:30:00Z"
}
```

**字段说明**：
- `eventType`: 事件类型，必填
- `eventData`: 事件数据，必填，JSON对象
- `businessId`: 业务ID，选填，用于关联业务对象
- `timestamp`: 事件时间，选填，默认为当前时间

**响应格式**：
```json
{
  "eventId": "evt_789012",
  "status": "ACCEPTED",
  "message": "事件已接收，将异步推送",
  "timestamp": "2026-09-06T10:30:01Z"
}
```

#### 3.2.2 事件验证
**验证内容**：
- eventType不能为空，且必须是系统支持的类型
- eventData不能为空，必须是合法的JSON
- 单个事件大小限制（如不超过1MB）

**验证失败处理**：
- 返回400错误
- 说明具体的验证失败原因
- 不进行存储和推送

### 3.3 通知推送

#### 3.3.1 订阅匹配
**功能说明**：事件发布后，自动匹配订阅了该事件类型的订阅者。

**匹配逻辑**：
```
1. 读取事件的eventType
2. 查询数据库：订阅了该eventType且状态为ACTIVE的订阅
3. 返回订阅列表（含callbackUrl、订阅者信息）
```

**并发推送**：
- 多个订阅者并发推送（线程池或异步任务）
- 各订阅者独立处理，互不影响
- 一个失败不影响其他订阅者

#### 3.3.2 HTTP推送
**功能说明**：向订阅者的回调URL发送HTTP POST请求。

**请求格式**：
```http
POST /webhook HTTP/1.1
Host: subscriber.example.com
Content-Type: application/json
X-Event-Id: evt_789012
X-Event-Type: ORDER_CREATED
X-Signature: sha256=abc123def456...

{
  "eventId": "evt_789012",
  "eventType": "ORDER_CREATED",
  "timestamp": "2026-09-06T10:30:00Z",
  "data": {
    "orderId": "ORD20260906001",
    "userId": "USR123",
    "amount": 299.00
  }
}
```

**请求头说明**：
- `Content-Type`: application/json
- `X-Event-Id`: 事件唯一ID
- `X-Event-Type`: 事件类型
- `X-Signature`: 签名（可选，如果订阅时提供了密钥）

**超时设置**：
- 连接超时：5秒
- 读取超时：30秒
- 总超时：35秒

**成功判定**：
- HTTP状态码为 2xx（200-299）
- 响应体可选（不校验内容）

**失败判定**：
- HTTP状态码非 2xx
- 网络异常（连接超时、读取超时、DNS解析失败）
- 订阅者服务不可用

#### 3.3.3 失败重试
**功能说明**：推送失败后，自动进行重试。

**重试策略**：
```
重试次数   延迟时间      累计时间
第1次     1分钟后      1分钟
第2次     5分钟后      6分钟
第3次     15分钟后     21分钟
第4次     1小时后      1小时21分钟
第5次     4小时后      5小时21分钟
```

**重试算法**：指数退避（Exponential Backoff）
- 第n次重试延迟 = min(初始延迟 * 2^(n-1), 最大延迟)
- 初始延迟：1分钟
- 最大延迟：4小时
- 最大重试次数：5次

**重试实现**：
- 使用延迟队列或定时任务
- 到达重试时间后自动触发
- 重试期间不阻塞新事件处理

**最终失败**：
- 超过最大重试次数后，标记为最终失败
- 记录失败原因和详情
- 触发告警（可选）

#### 3.3.4 幂等性保证
**问题场景**：由于重试机制，订阅者可能收到重复通知。

**解决方案**：
- 每个通知携带唯一的eventId
- 订阅者根据eventId进行幂等性处理
- 系统提供幂等性最佳实践文档

**订阅者实现建议**：
```java
// 订阅者端伪代码
if (已处理过该eventId) {
    return 200; // 直接返回成功，避免重复处理
}
处理业务逻辑();
记录eventId为已处理();
return 200;
```

### 3.5 监控告警

#### 3.5.1 实时监控
**监控指标**：
- 事件发布量（QPS）
- 通知推送量（QPS）
- 通知成功率
- 平均推送延迟

**展示方式**：
- 实时数值
- 趋势图表
- 状态面板

#### 3.5.2 告警规则
**告警场景**：

| 告警项 | 触发条件 | 级别 | 处理建议 |
|--------|----------|------|----------|
| 订阅者连续失败 | 某订阅者连续失败10次 | 高 | 检查订阅者服务状态 |
| 队列积压 | 待处理事件 > 10000 | 中 | 检查系统负载，考虑扩容 |
| 推送成功率下降 | 1小时内成功率 < 90% | 中 | 排查网络或订阅者问题 |
| 系统异常 | 系统进程停止 | 高 | 立即重启服务 |
| 推送延迟过高 | 平均延迟 > 10秒 | 低 | 检查系统性能 |

**告警方式**：
- 日志记录
- 邮件通知
- 钉钉/企微通知（可选）

## 4. 用户交互流程

### 4.1 订阅者注册流程

```
[订阅者] 准备回调接口 → [系统] 提供订阅API
           ↓
[订阅者] 调用订阅API
           ↓
[系统] 验证参数 → 创建订阅记录
           ↓
[系统] 返回订阅ID → [订阅者] 保存订阅ID
           ↓
[订阅者] 等待接收通知
```

### 4.2 事件发布与推送流程

```
[业务系统] 业务事件发生
           ↓
[业务系统] 调用发布API → [系统] 接收事件
           ↓                    ↓
[业务系统] 收到成功响应    [系统] 异步处理
           ↓                    ↓
[业务系统] 继续业务流程    [系统] 匹配订阅者
                                ↓
                           [系统] 并发推送
                                ↓
                           [订阅者] 接收通知 → 处理业务 → 返回200
                                ↓
                           [系统] 记录成功
                           
如果失败：
[系统] 记录失败 → 延迟重试 → 继续推送 → 直到成功或达到最大次数
```

### 4.3 通知查询流程

```
[用户] 需要查询通知状态
         ↓
[用户] 提供查询条件（eventId/subscriptionId/时间范围等）
         ↓
[系统] 查询数据库 → 返回通知记录
         ↓
[用户] 查看推送状态、响应详情
         ↓
[用户] 根据结果排查问题
```

## 6. 接口规范

### 6.1 RESTful API设计原则
- 使用标准HTTP方法（GET/POST/PUT/DELETE）
- URL使用名词，不使用动词
- 返回合适的HTTP状态码
- 统一的错误响应格式

### 6.2 API列表

#### 订阅管理
```
POST   /api/v1/subscriptions          创建订阅
GET    /api/v1/subscriptions          查询订阅列表
GET    /api/v1/subscriptions/{id}     查询单个订阅
PUT    /api/v1/subscriptions/{id}     更新订阅
DELETE /api/v1/subscriptions/{id}     删除订阅
```

#### 事件发布
```
POST   /api/v1/events                 发布事件
GET    /api/v1/events/{id}            查询事件详情
```

#### 通知查询
```
GET    /api/v1/notifications          查询通知列表
GET    /api/v1/notifications/{id}     查询单个通知
GET    /api/v1/events/{eventId}/notifications  查询事件的所有通知
```

#### 统计查询
```
GET    /api/v1/statistics/summary     统计概览
GET    /api/v1/statistics/events      事件统计
GET    /api/v1/statistics/subscriptions  订阅者统计
```

### 6.3 响应格式

**成功响应**：
```json
{
  "code": 200,
  "message": "success",
  "data": {
    // 具体数据
  }
}
```

**错误响应**：
```json
{
  "code": 400,
  "message": "参数验证失败",
  "errors": [
    {
      "field": "callbackUrl",
      "message": "URL格式不正确"
    }
  ]
}
```

## 8. 安全设计

### 8.1 API认证
- 使用API Key进行认证
- HTTP Header: `X-API-Key: your_api_key`
- 不同业务系统分配不同的API Key

### 8.2 签名验证
**目的**：订阅者验证通知的真实性，防止伪造。

**签名算法**：
```
1. 将请求体（JSON字符串）与密钥拼接
2. 使用HMAC-SHA256计算签名
3. 将签名放入HTTP Header: X-Signature
```

**订阅者验证**：
```java
String signature = request.getHeader("X-Signature");
String body = request.getBody();
String computed = hmacSha256(body, secretKey);
if (!signature.equals(computed)) {
    return 401; // 签名验证失败
}
```

### 8.3 HTTPS
- 生产环境强制使用HTTPS
- 保护数据传输安全

### 8.4 访问控制
- 订阅者只能查询自己的订阅和通知
- 业务系统只能发布自己的事件
- 管理员可以查看所有数据

- ERROR：系统错误、推送失败

**日志内容**：
- 时间戳
- 日志级别
- 事件ID/通知ID
- 操作描述
- 耗时
- 结果
